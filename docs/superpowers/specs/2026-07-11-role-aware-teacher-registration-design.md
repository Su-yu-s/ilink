# iLink 角色化注册与教师资料实施记录

- 设计日期：2026-07-11
- 文档更新：2026-08-15
- 状态：已完成并纳入当前产品规则

## 1. 问题与目标

旧逻辑把“教师账号”和“导师申请”当作两个无关流程，导致教师通过注册页创建账号后仍会看到“申请成为导师”，个人中心也继续展示年级等学生字段。

本次改造建立统一规则：注册页选择 `TEACHER` 就表示用户已经以教师身份进入平台，并自动获得可维护的导师档案。新档案先标记为 `INCOMPLETE`，资料完整后自动公开，不需要再次申请或等待管理员审核。

## 2. 已落地规则

- 公开注册只接受 `STUDENT` 或 `TEACHER`，不允许注册管理员。
- 教师账号和一条状态为 `INCOMPLETE` 的导师档案在同一事务中创建；导师档案保存失败时注册事务回滚。
- 教师身份在注册后立即启用；补全姓名、任职单位、专业领域、职称、研究方向和简介后，档案自动转为 `APPROVED` 并进入公开列表。
- 教师在导师招贤页看到“我的导师主页”，不会看到“申请成为导师”。
- 学生仍可使用历史兼容流程申请成为导师，生成 `PENDING` 档案并等待管理员审核。
- 教师只能维护自己的导师档案；学生不能调用教师档案修改接口。

## 3. 数据映射

| 范围 | 学生语义 | 教师语义 | 存储位置 |
| --- | --- | --- | --- |
| 通用 | 用户名、姓名、邮箱、头像、性别、个人简介 | 同左 | `user` |
| `school` | 学校 | 任职单位 | `user.school` |
| `college` | 学院 | 院系/部门 | `user.college` |
| `major` | 专业 | 专业领域 | `user.major` |
| `grade` | 年级 | 不读取、不展示 | `user.grade` |
| 导师资料 | 不适用 | 职称、研究方向、导师简介、代表项目 | `teacher_application` |

导师档案保留独立状态，是因为学生升级为导师的兼容流程仍需管理员审批，同时需要区分教师账号身份与公开资料完整度。教师注册产生的档案写入 `INCOMPLETE`，完整后自动写入 `APPROVED`。

## 4. 页面行为

### 注册页

- 学生/教师切换会把“学号”同步切换为“工号”。
- 提交数据中的 `role` 只允许 `STUDENT` 或 `TEACHER`。
- 教师注册成功提示身份已经启用，不引导用户重复提交导师申请。

### 导师招贤

- 未登录用户只浏览导师。
- 学生显示“申请成为导师”，继续使用兼容升级流程。
- 教师显示“我的导师主页”或完善资料提示；页面通过 `GET /api/teacher/me` 找到自己的导师档案。
- 列表只查询状态为 `APPROVED` 的档案。

### 个人中心与公开主页

- 学生展示学校、学院、专业、年级。
- 教师展示任职单位、院系/部门、专业领域，并隐藏年级。
- 教师编辑页额外加载职称、研究方向、导师简介和代表项目。
- 账号资料与导师档案分别保存，错误信息明确指出失败的部分。

## 5. 接口契约

| 接口 | 行为 |
| --- | --- |
| `POST /api/register` | 创建用户；教师同时创建 `INCOMPLETE` 导师档案并立即启用导师身份 |
| `GET /api/teacher/list` | 仅返回 `APPROVED` 导师 |
| `GET /api/teacher/{id}` | 返回公开导师资料及关联用户摘要 |
| `GET /api/teacher/me` | 登录教师读取自己的导师档案 |
| `PUT /api/teacher/profile` | 仅当前 `TEACHER` 更新自己的导师档案 |
| `POST /api/teacher/apply` | 学生兼容升级流程，创建 `PENDING` 导师申请 |
| `POST /api/teacher/project-apply` | 学生向已批准导师提交合作申请 |
| `GET /api/teacher/my/project-applications` | 教师读取待处理合作申请 |
| `PUT /api/teacher/project-application/{id}/approve` | 导师批准或拒绝自己的合作申请 |

## 6. 数据迁移

- `V14__add_teacher_professional_title.sql` 为导师档案增加独立职称字段。
- `V15__backfill_registered_teachers_as_mentors.sql` 为已有教师账号补齐导师档案。
- `V17__enforce_teacher_profile_completeness.sql` 将旧空白公开档案回填为 `INCOMPLETE`，资料完整后由业务服务自动公开。
- `teacher_application.user_id` 的唯一约束防止同一账号产生多个导师档案。

## 7. 验证覆盖

当前自动化测试直接覆盖：

- 教师注册创建 `INCOMPLETE` 导师档案，完整资料保存后自动变为 `APPROVED`。
- 未登录用户不能读取当前教师私有档案。
- 教师可以更新自己的导师档案。
- 学生不能更新导师档案。

页面验收还应持续检查：教师注册后无需再次申请、完整资料后能在导师墙看到自己、教师资料无学生年级字段、学生提交合作申请后教师能够处理，以及桌面与移动端字段标签一致。

## 8. 后续修改约束

- 不得重新把教师注册降级为“导师候选申请”；`INCOMPLETE` 只表达资料未完成，不代表等待管理员批准。
- 不得只在前端隐藏入口而保留互相矛盾的后端身份逻辑。
- 新增教师资料字段时，应先确定属于账号通用信息还是导师专业信息，再选择 `user` 或 `teacher_application`。
- 学生升级导师的兼容流程可以单独演进，但不能影响教师注册后立即获得导师身份、完整后自动公开的规则。
