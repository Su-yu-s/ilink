# AI 协作模块系统一体化界面设计

> 本文是团队 Agent 工作台的视觉子规范。功能边界、角色权限、API、数据模型、安全、测试和分阶段实施方案，一律以《[2026-10-22-team-agent-workbench-design.md](2026-10-22-team-agent-workbench-design.md)》为准；两文冲突时以主设计文档为准。

- 文档版本：2.6（与主设计文档同步的设计冻结候选稿）
- 日期：2026-10-22
- 状态：视觉方向已确认，设计边界已收口，等待用户复核后进入实施计划
- 影响范围：团队空间 AI 协作模块、AI 协作交互 Demo、相关公共状态样式
- 不包含：首页、社区、竞赛、成果展示、个人中心等页面的整体重做

本文不声明任何功能已经完成。Demo 中的文档、表格、邀请、保存和审计交互只用于验证视觉与交互可能性，除非主设计文档已将其列入正式阶段并通过验收。

## 1. 背景

现有 AI 协作交互 Demo 以模拟数据展示了 Agent 会话、执行计划、动作确认、协作文档、协作表格和日常杂活，但 Demo 使用了一套独立的顶栏、左侧工作台、卡片与状态样式，视觉上像一个脱离 iLink 的新产品。

用户确认本轮不是重做全站，而是让 AI 协作设计保持系统一致性：

- AI 协作是团队空间中的一个工作面板，不是独立应用。
- 页面外壳、字体、间距、组件和状态反馈必须继承 iLink 现有团队空间。
- 只有 Agent 会话、执行记录和动作确认可以增加正式第一阶段专用结构；文档画布和表格画布只作为后续候选或明确标注的 Demo。
- 已确认的明亮状态色应成为统一语义色，不在 AI 模块内部另造一套颜色。

## 2. 目标

1. 保留已确认且真实存在的 Agent 会话、执行记录和动作确认交互，不把 Demo 的模拟业务能力等同于正式功能。
2. 消除 Demo 中与全站脱节的独立页面外壳和视觉令牌。
3. 建立 AI 协作模块与团队空间现有组件之间的明确映射。
4. 提升信息层级、阅读节奏、组件状态和响应式表现。
5. 确保后续接入正式 `team-space.html` 时无需再维护第二套视觉系统。

## 3. 非目标

- 不重做共享页头、页脚和全站导航。
- 不对所有业务页面做结构调整或重新排版。
- 本视觉文档本身不改变任务、成员、资料、群聊、权限或 AI 接口的数据结构；正式后端改动由主设计文档定义。
- 不把 Demo 的模拟保存、邀请、审计行为直接当作真实后端能力。
- 不引入新的前端框架或组件库。

## 4. 设计原则

### 4.1 系统原生

AI 协作必须表现为团队空间的一个工作面板：

- 外层继续使用 `il-header`、`main-content`、`workspace-layout` 和团队侧栏。
- AI 面板继续位于 `#ai-panel`，不复制全站顶栏或第二个团队导航。
- 内容区使用现有页面背景、表面层级、圆角、边框和阴影强度。

### 4.2 一个动作只有一个主焦点

- Agent 会话是主内容焦点。
- 当前执行计划与待确认动作是次焦点。
- 团队数据与审计信息降低对比度，作为上下文存在。
- 左侧导航、右侧指标和能力入口不得同时使用高对比度强调。

### 4.3 状态先语义、后颜色

- 颜色不能单独表达状态。
- 成功、警告和错误必须同时包含图标或文字。
- 绿色可以表示开放/正向状态，例如招募中、在线、审核通过、执行成功和完成；侧栏、主按钮等“当前选中容器”仍使用系统既定品牌与中性色，不把大块选中面改成状态绿。
- 黄色只表示临期、等待确认、需要注意。
- 红色只表示错误、逾期、危险操作。

### 4.4 页面特色服从系统规则

首页古诗词、竞赛目录、成果详情和团队工作台可以保留各自版式特色，但 AI 协作模块的按钮、输入框、标签、弹窗和提示必须与当前系统一致。

## 5. 系统继承边界

### 5.1 直接复用的系统能力

| 能力 | 系统来源 | AI 模块用法 |
| --- | --- | --- |
| 页面顶栏 | 共享页头片段 | 原样使用，不复制 |
| 团队侧栏 | 团队空间导航 | “AI 协作”作为当前面板 |
| 页面容器 | 团队空间主内容区 | 保持现有宽度与左右留白 |
| 按钮 | 全站 `.btn` 体系 | 确认、取消、撤销、导出 |
| 表单控件 | 全站 input/select/textarea | 对话输入；文档编辑和表格单元格仅限后续阶段或明确标注的 Demo |
| 状态标签 | 全站 badge/status 规则 | 执行中、待确认、成功、失败 |
| 弹窗 | 全站 modal 规则 | 权限、删除、名称冲突确认 |
| Toast | `Toast` 公共组件 | 成功、错误、加载和撤销 |
| 动效与焦点 | 全站 tokens | 悬停、按下、键盘焦点、减弱动效 |

### 5.2 AI 模块新增的专用结构

正式第一阶段只允许以下与已确定能力对应的新增结构：

- Agent 会话消息与执行步骤。
- 执行计划卡和逐项动作确认。
- 待确认动作与撤销入口。
- Agent 产出的审计记录。

文档协作画布、表格协作画布和实时协作属于后续候选能力。它们可以继续作为视觉 Demo 保留，但不得进入正式导航、不得显示“已保存/已协作/已审计”等正式成功反馈，除非主设计文档对应阶段已完成并通过验收。

这些结构必须使用系统现有排版、按钮、表单和状态规则，不定义新的品牌颜色或独立外壳。

## 6. 状态色系统

三种明亮状态色作为共享语义色使用，AI 模块不再维护局部近似色。

绿色、黄色和红色是状态语义色，不作为全站主品牌底色或大面积装饰。主按钮、页面背景和选中容器继续沿用系统既定中性色与品牌层级；状态色只用于图标、描边、小标签、短横条和小面积反馈。

### 6.1 状态基准色

- 成功、在线等正向状态：翡翠绿 `#00A86B`
- 警告、临期、等待确认：琥珀金 `#F2A900`
- 错误、逾期、危险操作：亮珊瑚红 `#E64B4B`

### 6.2 小面积浅色底

- 成功浅底：`#E9F8F1`
- 警告浅底：`#FFF6E3`
- 错误浅底：`#FDECEC`

### 6.3 可读文字色

状态色用于图标、圆点、描边和小面积强调。用于小字号文字时使用对应深色：

- 成功文字：`#087A50`
- 警告文字：`#9C6500`
- 错误文字：`#B92F2F`

所有状态组件必须通过对比度检查，颜色不得作为唯一识别方式。

明亮基准色和可读色承担不同职责。在白色/浅灰表面上：

- `#087A50`、`#9C6500`、`#B92F2F` 对白色的对比度分别约为 `5.37:1`、`4.91:1`、`5.98:1`，可用于小字号状态文字。
- 对各自浅色底，对比度分别约为 `4.90:1`、`4.57:1`、`5.24:1`，仍满足普通文字的最低对比度。
- `#F2A900` 对白色只有约 `2.01:1`，不得直接作为白底细图标、细描边或小字号文字；需要时可作为实心底色，并搭配深色文字/图形和清晰边界。
- `#00A86B`、`#E64B4B` 可用于满足非文本对比要求的图形或填充，但状态含义仍必须同时提供图标或文字。

### 6.4 业务状态映射

状态色只在标签、圆点和短边条中使用，不把整张卡片铺色：

| 状态 | 表现 |
| --- | --- |
| 团队“招募中” | 绿色文字/圆点，保持现有克制标签样式 |
| 团队“已组队”“已结束” | 中性灰，强调文字而非背景 |
| 任务“进行中” | 使用系统现有主文字层级和进度反馈，不新造第三种品牌色 |
| 任务“审核中”、动作“待确认” | 琥珀色语义 |
| 任务“已完成”、动作“成功” | 绿色语义 |
| 任务“逾期”、动作“失败” | 红色语义 |
| 任务“已取消”、动作“已取消/已过期” | 中性灰，不显示为错误红色 |

## 7. 布局设计

### 7.1 正式页面布局

AI 协作接入正式团队空间后：

- 页面顶部继续使用共享 iLink 页头。
- 页面主体继续使用团队空间侧栏和主内容区。
- `#ai-panel` 内部采用“Agent 主会话 + 执行上下文”布局。
- 桌面端 Agent 会话约占可用宽度三分之二，执行上下文约占三分之一。
- 会话区与执行上下文都位于现有工作面板内部，不再各自成为独立应用卡片。
- 后续阶段的文档和表格画布可以在当前 AI 面板内部展开，不跳转到另一个视觉系统；第一阶段或 Demo 必须明确标注其模拟状态。

### 7.2 信息层级

1. 当前团队与竞赛上下文。
2. Agent 身份、模式和工作状态。
3. Agent 会话正文。
4. 下一步建议和快捷能力。
5. 待确认动作与审计信息。
6. 输入区。

### 7.3 空状态

- 首次进入显示 Agent 欢迎语、团队快照、三个主能力和最多三个次级入口，不为凑数展示未实现能力。
- 空状态在空间充足时可垂直居中。
- 内容高于可视区时必须从顶部开始并可完整滚动。
- 用户发送第一条消息后，欢迎区折叠为普通会话历史，不继续占据整屏。

### 7.4 后续文档与表格画布

- 本节只约束后续候选能力或 Demo，不表示正式第一阶段已经提供文档/表格。
- 画布头部使用系统按钮和返回规则。
- 文档正文采用适合阅读的最大宽度，避免超宽屏行长过大。
- 表格工具栏、状态选择、添加行和导出按钮使用系统控件。
- 画布内不出现新的品牌标识或全站顶栏。

## 8. 排版与组件规格

### 8.1 字体

- 继承全站字体栈与中英文规则。
- 正文以 `14px` 为基准，行高约 `1.7`。
- 欢迎区主标题使用系统大标题尺度，不使用营销页巨型字号。
- 辅助信息最小为 `12px`，不再大量使用 10–10.8px 的过小文字。
- 数字、日期和进度使用等宽数字。

### 8.2 表面与圆角

- 页面表面、次级表面、悬停底色沿用现有系统令牌。
- 普通组件圆角保持系统卡片的 `12px` 档。
- 只有小标签和小按钮使用更小圆角，不额外引入装饰性胶囊。
- 阴影只用于输入框、浮层、弹窗和真正离开页面的元素。

### 8.3 导航选中

- 当前“AI 协作”沿用团队侧栏现有选中样式。
- 不增加独立黑色大块导航或 AI 专属侧栏。
- 选中状态必须有文字、形状或位置变化，不仅依赖颜色。

### 8.4 能力卡

- 使用团队空间卡片表面与边框。
- 图标、标题、短说明形成固定层级。
- 悬停只提高边框和表面层级，不做大幅位移。
- 点击后显示按压和加载状态。

### 8.5 输入区

- 输入区视觉与团队群聊输入框同源。
- 焦点状态使用系统焦点环。
- 发送按钮是输入区唯一高对比主按钮。
- 多行输入自动增长，但设置最大高度并内部滚动。

## 9. 交互设计

### 9.1 Agent 能力模式

- 正式页面的“只读”和“可执行 · 需确认”是后端 `capabilities` 返回的能力态，不是前端可自行切换的授权开关。
- 用户可以表达“只分析”或“生成可执行计划”的当前意图，但后端能力为只读时只能得到分析和预览；输入区必须同步说明动作不可用及原因。
- Demo 可以模拟能力态切换；正式接入不得让客户端通过请求参数、按钮或本地状态提高权限。
- 只读能力态仍可分析、展示结果预览和编辑尚未发送的输入文本，但不能保存为正式草稿或执行写操作。

### 9.2 执行流程

1. 用户选择能力或发送请求。
2. Agent 展示执行步骤和将读取的数据范围。
3. Agent 给出结果和逐项动作计划。
4. 用户勾选、取消或忽略动作。
5. 用户点击确认后执行。
6. 系统展示执行结果、审计记录和撤销入口。

执行步骤必须显示真实状态：等待、执行中、完成、失败。禁止只使用整个面板的统一透明加载。

动作组视觉状态必须与后端一致：用户点击确认后的本地请求可显示“正在执行并锁定”，但 `CONFIRMING` 是后端事务内标记，不得被页面当成可长期轮询的持久状态。成功后选中项显示完成、未选项显示取消；可判定的业务失败才把整组显示为失败，并说明“未写入任何业务数据”。数据库异常或网络结果未知时显示“结果未确认，可安全重试”，页面必须使用相同请求 ID 重放或重新读取后端，不能自行伪造 `FAILED` 或“全部已回滚”。任何情况都不得出现一部分绿色成功、一部分红色的伪部分成功。单个已执行动作的撤销状态独立显示“可撤销/正在撤销/已撤销/已过期/不可撤销”；动作组本身仍保持“已执行”结果。

动作卡只在其来源运行已经成功完成且后端已持久化动作组后进入可确认状态。流式阶段可以显示“正在整理可执行计划”的本地占位，但不得显示可点击确认按钮；运行失败或取消后移除该占位，不留下幽灵动作。

### 9.3 反馈

- 成功：只有后端确认持久化完成后，才使用全站 Toast、绿色完成标记和结果摘要；Demo 使用“模拟完成”文案。
- 警告或需要确认：使用黄色状态图标和明确动作按钮。
- 错误：保留用户输入，显示具体原因和重试入口。
- 可撤销动作：结果卡内保留撤销按钮，直到失效或用户离开。
- 引用和附件只通过受控来源卡、内部详情或受鉴权下载入口打开；Agent 正文不自动加载远程图片、媒体或跟踪像素。
- 流式回答只能使用统一的受限 Markdown 渲染器处理累积缓冲，不能把模型片段直接写入 `innerHTML`。终态后用服务端最终清洗结果替换；流式阶段不激活任何原始链接或远程媒体。
- 所有 Toast 不遮挡共享页头。

### 9.4 动效

- 悬停与状态切换：约 `140–180ms`。
- 卡片展开和画布切换：约 `180–240ms`。
- 支持 `prefers-reduced-motion`，减少位置移动和非必要缩放。

## 10. 响应式规则

沿用团队空间现有断点，不另建一套。

### 10.1 宽屏桌面

- 保留完整团队侧栏和 AI 内部双栏。
- 会话正文限制最大可读宽度。

### 10.2 中等桌面与平板

- 在现有窄屏断点下压缩侧栏和执行上下文。
- 指标与待确认动作可以下移，但不能覆盖会话或输入区。

### 10.3 手机

- 团队侧栏继续使用现有抽屉式操作。
- AI 内部改为单列：会话、动作、团队上下文顺序排列。
- 输入区在进入会话视图时保持可见。
- 文档和表格画布使用单列工具区。
- 页面不得产生横向滚动。

### 10.4 低高度窗口

- 页面外壳允许正常滚动。
- Agent 消息区内部滚动，输入区固定在工作面板底部。
- 欢迎内容高于可用空间时按正常文档流从顶部显示。

## 11. 可访问性

- 所有按钮必须有可见焦点状态。
- 图标按钮必须有 `aria-label`。
- 执行计划勾选项必须可键盘操作。
- 动态执行状态通过 `aria-live="polite"` 播报阶段变化、失败和完成，不逐 token 播报流式正文。
- 错误提示与对应字段或动作建立可理解关联。
- 触摸目标不小于约 `40px`，小屏优先满足 `44px`。
- 状态信息不只依赖颜色。

## 12. 视觉一致性验收

将 AI 协作页面与团队空间其他面板并排检查：

1. 页头完全相同，不出现第二个顶栏。
2. 页面背景、主内容宽度和左右留白一致。
3. 团队侧栏导航位置、宽度和选中规则一致。
4. 标题、正文、辅助文字的字号与行高来自同一套层级。
5. 按钮、输入框、标签和弹窗在同等状态下外观一致。
6. 卡片圆角、边框、阴影强度与团队空间其他面板一致。
7. 绿色、黄色、红色在同一语义下与全站一致。
8. AI 模块独有结构看起来是业务扩展，而不是另一个产品。
9. 引用卡、附件卡和错误反馈沿用同一套安全链接与焦点规则，不因 AI 内容引入第三方媒体自动加载。

## 13. Demo 与正式接入的验收边界

以下条目是 Demo 的视觉与交互验收，不代表正式系统功能：

1. Demo 中的能力入口可以触发对应模拟流程。
2. Demo 中只读与可执行能力态的模拟切换正确，并明确这是模拟状态。
3. 动作勾选、确认、忽略、执行、撤销和审计状态正确。
4. 文档和表格画布在 Demo 中具有明确“模拟数据”标识，不伪装为已接入后端的正式能力。
5. Demo 不展示真实用户隐私、真实文件 URL 或不存在的持久化结果。

以下条目才是团队空间正式接入时必须满足的视觉验收：

1. 工作台使用共享页头、团队侧栏和主内容容器。
2. 只读与可执行能力态由后端真实权限和能力驱动，前端不能自行切换成更高权限。
3. 动作卡只展示当前用户可执行的动作，确认、失败、过期和撤销状态真实。
4. 成功、警告、错误和加载反馈明确且不遮挡页头。
5. `1440px`、`1280px`、`1024px`、`768px`、`390px` 下无横向溢出。
6. 低高度窗口下输入区仍可见，消息区可内部滚动。
7. 键盘可完成模式切换、能力选择、动作勾选和确认。
8. 首页及其他非目标页面不发生布局或组件结构调整；更新共享状态语义色时，仅同步颜色，不重新排版。

历史 Demo 验收项“文档编辑、邀请展示、保存反馈、表格编辑、完成度计算、添加行和 CSV 导出”暂不进入正式接入清单，只有对应后端与安全验收完成后才能移回正式清单。

## 14. 实施边界

- 交互 Demo 只承担方案验证，不替代正式团队空间，也不作为论文中的“已实现能力”证据。
- 正式接入前保持现有后端接口和权限行为不变。
- 新样式优先通过共享语义令牌和现有组件扩展实现。
- 如必须新增 AI 专用变量，统一使用 `--il-agent-*` 前缀并限制在 AI 面板作用域。
- 禁止在 AI 模块内复制一套独立颜色、按钮、输入框、弹窗或 Toast。
